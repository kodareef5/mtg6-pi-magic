# Rules for text a model reads

Read the root writing rules before editing prompts, skills or tool descriptions.
Text must match the handlers a seat can use today.

## State the limits

Each tool description says what it does and what success does not guarantee.
A view can be stale, an accepted pick is not necessarily a resolved effect, and
listing a prepared procedure does not certify its card interpretation or rules
legality. Resource validation checks the stated cost, not whether the card
requires that cost.

## Give facts and preserve choice

Describe sources, costs, effects, timing and alternatives at equal detail.
Strategy belongs in attributable, revisable seat guidance, not in tool prose
that makes every seat prefer the same move.

Describe listed picks first. Keep every id unchanged. Prepared procedures and
unique delegated continuations work; raw declarations, free-form delegation,
option widening and objections with remedies remain unfinished. Do not
advertise an executable route whose handler does not exist.

## Show the payment

A reader must be able to compare choices without decoding an id. Name the
source and incarnation, mana colors and persistence, stated cost and effects.
Explain arithmetic when a number alone would hide how it was obtained.

## Keep context small and sufficient

Keep every fact needed for the decision, including restrictions and unresolved
public stack instructions. Registered deck counts are public; hidden object
identities and library order are not.

The classifier receives the plan's objective, the due step, the next two, live
branches, holds and stops, and the options marked with the plan. Procedure
bodies and card registrations stay with strategy, which receives the whole plan
and its progress when it writes the next one.
