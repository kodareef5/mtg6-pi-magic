# Writer completion coverage

The three [post-entry repairs](2026-10-07-post-entry.md) left their current main
window without an authored completion policy. Two selected winning attacks,
but neither established complete execution coverage. The writer's syntax check
accepts that omission, while Jev's contract says missing policy grants no pass.

The opt-in `completion` benchmark arm checks the fully expanded plan. It uses
existing `phases[].when` and `complete: pass | ask`; it adds no core syntax,
stored progress, generated default, physical action or planner session.
The ordinary writer, pregame defaults and historical journals remain unchanged.

## Required scope

- A turn plan covers the current and remaining normal priority windows through
  its context-stamped `throughTurn`. Current-turn steps come from the projected
  remaining schedule, including inserted or repeated steps. Future turns use
  the ordinary schedule, not a prediction of effects or surviving objects.
- Preparation starts at its labelled next upkeep and covers the following turn.
- A narrow opponent-turn response repair checks only its current window. It
  retains unaffected policies without demanding a replacement next-turn plan.
- Untap and ordinary cleanup have no priority requirement. An actual current
  cleanup priority decision does need coverage.

An authored broad `when` can cover several windows. Matching `pass` and `ask`
policies conflict and are reported together; no precedence is inferred. The
validator reports every uncovered window in one refusal and never chooses
either policy. `ask` is valid syntax, including a broad request for help. Its
usefulness is graded separately. Coverage certifies neither response decisions
nor strategic quality.

False conditions remain false only at the current position, with no execution
credit. Available branches, unavailable required actions, stack prerequisites,
matching marks, physical options and ordering remain unchanged. This arm does
not change the pilot renderer or teach it a new completion rule. A pass while
the stack is nonempty lets resolution continue; it does not prove a step or
window finished. The seat still applies the authored response policy.

## Gate declared before inference

Offline checks cover all three frozen missing-completion repairs, authored
`ask` and `pass`, conflicting overlaps, bounded windows, preparation, narrow
response scope, retained amendments, actual cleanup priority, branch availability,
false-condition status, unchanged options and progress, and replay/clone.

Freeze production and treatment requests at the post-entry checkpoint. The
production request must match the previous freeze. Treatment may add only the
completion window list, coverage problems and a task suffix requiring explicit
authored closure. System prompt, tools, output ceiling, facts, brief and base
remain identical. The check runs after normal reuse expansion.

Run three repairs with the ordinary Luna-low roster, 4,000 ceiling and three-reply
budget. Complete the whole batch. Measure acceptance, refusals, coverage and
latency separately from winning commitments. An unresolved reply has no plan;
never substitute the old plan or extend the reply budget.

The execution mechanism is measured separately from strategy. Play every
accepted treatment plan and the three frozen `cc67778` control repairs through
the same shared runner, alternating arms within each repetition. Bound each at
the end of turn 15, 80 new recorded decisions, or two actual judge attempts;
stop on any gap. The decision limit includes forced and delegated rows and is
net ledger growth, so the independent judge-attempt bound also prevents rollback
cycles. Stops remain separate from outcomes. Green plays live in all six.

For each continuation, report:

- Red help where the current items are all recorded or absent is the primary
  coverage measure. Report windows containing false-conditional items separately:
  the unchanged pilot wording says they are not completed, so persistent help
  there could have a separate rendering cause. Count relevant decision exposures
  and stack state alongside help; an earlier win or stop can remove exposures.
- Red foreground repairs, all-seat help, latency and preparation readiness.
- Available response branches passed over, target/payment/waiting obedience,
  legal play, outcomes, gaps, fallback and replay/clone health.

Lower help only supports this mechanism when the relevant exposures and causes
agree, without branch or policy-obedience regression, gaps or fallback. Zero
baseline target-help establishes no improvement. Broad routine `ask` is a manual
usability failure. These counts are not reliability rates, and the plans may
differ in strategy: this tests the writer contract as a whole, not `complete`
alone.

Strategy still requires three feasible winning lines with consistent execution
policies before adoption or later strategic expansion. This execution comparison
does not waive the failed generation gates. It neither changes the default nor
authorizes a full game. A positive would still need the existing response,
stack-waiting and development guards.
